# async_compute_probe

Can a compute-only GPFIFO channel run next to the 3D channel on the GR engine of a GB202, through the RM channel
path NVK on RM uses? The probe uses librmclient only (no Vulkan): it builds TSGs, ctxshares (VEIDs), channels and
objects in several layouts, runs busy-wait compute work on each channel and reports whether the channels overlap.
The `async` scenarios use the layout NVIDIA's own driver uses (`docs/research/async-compute-gb202.md`): the
compute channel in the graphics channel's TSG on its own ctxshare (VEID 1, 2), allocated with
`NV_CHANNEL_ALLOC_PARAMS.flags = GROUP_CHANNEL_RUNQUEUE_ONE | GROUP_CHANNEL_THREAD_ONE`. The header comment of
`async_compute_probe.c` has the full design and the sources of every method encoding.

| file | what |
|---|---|
| `async_compute_probe.c` | the probe |
| `spin_sass.h` | NAK SM120 machine code of `shader/spin.comp` (3 variants), generated by `gen-spin.sh` |
| `rm_params.h`, `clcdc0qmd.h` | RM parameter layouts, NVIDIA's QMD V05_00 header (MIT) |
| `build-windows.sh` | MinGW cross build to `out-win/async_compute_probe.exe` (librmclient compiled in, one file) |
| `build-linux.sh` | native build to `out-linux/async_compute_probe` (runs on a machine with NVIDIA's driver at the release librmclient expects; `CRM_RM_VERSION` overrides the check) |
| `mock/run-mock.sh` | the probe against a software RM and GPU (no hardware): logic check |
| `verify/verify.sh` | compares the hand-encoded compute pushes with Mesa's generated macros |

## Scenarios

| name | layout | runs work |
|---|---|---|
| `async` | one TSG: SYNC ctxshare (VEID 0) + channel A (3D, compute, copy); SPECIFIED VEID 1 + channel B (flags 0x10000010, compute); a copy object on B is tried afterwards | yes |
| `async-late` | as `async`, B created after the TSG is scheduled | yes |
| `async3` | SYNC + SPECIFIED VEIDs 1 and 2, three channels | yes |
| `sync2` | one TSG, one SYNC ctxshare, two channels on it | yes |
| `tsg2` | two TSGs, one channel each | yes |
| `async3d` | VEID 1 channel with a 3D object | no |
| `async-old` | ASYNC ctxshare (VEID 63), channel flags 0 | no |
| `m-*` | creation-only variants of channel B: `m-async-chf` (ASYNC + flags), `m-spec1-nochf` (VEID 1, flags 0), `m-spec1-rq1` (RUNQUEUE_ONE only), `m-spec1-thr1` (THREAD_ONE only), `m-spec8-chf`, `m-spec63-chf`, `m-lower-chf` (ASYNC_PREFER_LOWER), `m-chf-copy` (copy object on B), `m-bonly` (B without channel A) | no |

`--scenario matrix` selects every creation-only scenario: it allocates and frees RM objects and submits no GPU
work, so it can also run natively on a Linux host (`build-linux.sh`, then `out-linux/async_compute_probe
--scenario matrix`).

## Build

```sh
./build-windows.sh          # needs gcc-mingw-w64-x86-64 only; takes seconds
./build-linux.sh            # native
```

Both take `[REPO_DIR] [OUT_DIR]`; the default REPO_DIR is this checkout.

## Run in the Windows guest

Copy the exe into the guest's tools folder and run it there (it needs no desktop session):

```sh
scp -P 2222 out-win/async_compute_probe.exe "$WIN_SSH:C:/Users/Public/t/"
ssh -p 2222 "$WIN_SSH" 'C:\Users\Public\t\async_compute_probe.exe --scenario async'                 # about 5 s
ssh -p 2222 "$WIN_SSH" 'C:\Users\Public\t\async_compute_probe.exe --reps 21 --verbose'              # everything
ssh -p 2222 "$WIN_SSH" 'C:\Users\Public\t\async_compute_probe.exe --scenario async --xwait --reps 21'
ssh -p 2222 "$WIN_SSH" 'C:\Users\Public\t\async_compute_probe.exe --scenario async --contend --reps 21'
```

`--xwait` adds a cross-channel semaphore wait with and without ACQUIRE_SWITCH_TSG; `--contend` runs it while a
channel in another TSG keeps spinning; `--wgs 64 --k 8` makes each channel busier. Every CPU wait is bounded
(`--timeout-ms`, default 3000); a bad method raises an RC error on the probe's own channel, not a GPU hang.

## Output

Per scenario: `create` (ok, or `REFUSED <step>`), the VEID RM returned per channel, each channel's solo duration,
the makespan when all start together, overlap = share of the shorter channel's work that ran next to the other's,
and the verdict (CONCURRENT >= 75 %, SERIAL <= 25 %, else PARTIAL). Creation-only scenarios show `created` or the
refusal. `RESULT PASS` means the `async` scenario created its channels, both ran and every output marker was
written.

Expected on the RTX 5090: `async`, `async-late`, `async3` CONCURRENT with VEIDs 0/1 (0/1/2) and the copy object on
B refused (`NV_ERR_INVALID_STATE`); `sync2` and `tsg2` SERIAL; `async3d` and `async-old` refused
(`NV_ERR_INVALID_OBJECT`); `m-spec1-nochf` refused at the compute object, `m-spec1-thr1` at the channel
(`NV_ERR_INVALID_ARGUMENT`), every other `m-*` created.
